---
name: summarize-change-scope
description: Produce change summaries translating a decided solution's delta into concrete, ADR-traceable code changes. Use when summarizing, estimating, or documenting the implementation changes required for a solution.
---

<when-to-use-this-skill>
- User wants a change summary of the concrete code changes required to implement a decided solution
- User wants implementation scope estimated (file counts, LOC ranges), with or without code access
- User wants a change summary traceable to ADRs for feature delivery
- User wants to regenerate a change summary after findings or the solution doc changed
- Do NOT load when no findings doc / solution doc exists yet — `conduct-spike` produces them first
- Do NOT load to run a spike, write a solution doc, or draft ADRs — `conduct-spike`, `write-solution-doc`, `draft-adr` handle those
</when-to-use-this-skill>

<knowledge>

<change-summary-schema>
A change summary translates the delta between **findings** (current state) and **solution doc** (target state) into change items grouped by category, each cluster traceable to its ADR:

| Category | Meaning |
|---|---|
| New | create file/module/service |
| Modified | change existing code |
| Retired | deprecate/delete code |
| Configuration | env, flags, CI/CD, IaC |
| Data | schema changes, migrations |
| Dependency | adopt/remove a dependency |
| Test | new/updated test suites |

Include a **notes section** for caveats, assumptions, open questions. Format and per-category examples: **reference/change-summary-guide.md**.
</change-summary-schema>

<code-access-modes>
| Mode | Approach | Estimates |
|---|---|---|
| With code access | Trace findings' code paths; count files/packages, LOC ranges, classes to modify | Mark code-verified |
| Without access | Describe changes at architectural level from findings + solution doc | Mark unverified |

Always state which mode applies; never present unverified estimates as verified.
</code-access-modes>

<input-requirements>
Consumes the spike's artifact files: **findings doc** (current-state baseline), **solution doc** (target state), and **ADRs** (for tracing each change cluster). Read them before compiling — never generate from guesswork. If the artifacts are missing, do not proceed; ask the user to share them or let `conduct-spike` produce them.
</input-requirements>

<consumer>
The change summary is consumed by **orchestrate-feature-delivery** (decomposed into features/phases) and regenerated by `conduct-spike`'s **sync-update-artifacts** whenever findings or the solution doc change. The change summary is **never final** — recompute whenever its baseline or target changes.
</consumer>

<capabilities>

<compile-change-summary>
1. Load the input artifacts: findings doc (current state), solution doc (target state), ADRs (for tracing). If any is missing, ask the user to share it — do not compile from guesswork.
2. Determine code access: ask "Can I access the current codebase to verify the scope of changes?" Record **code-verified** or **unverified** per **code-access-modes**.
3. Map the delta per area/ADR using **change-summary-schema** categories; group by area/service, label each cluster with its ADR reference; identify cross-cutting concerns.
4. Compile per **reference/change-summary-guide.md** with a notes section; save to `<spike-folder>/change-summary.md`.
5. Present and ask: "Does this change scope look accurate? Anything missing, overestimated, or underestimated?"
6. The change summary is **never final** — to regenerate after findings or the solution doc change, rerun these steps seeded with the updated artifacts (as `conduct-spike`'s **sync-update-artifacts** does).
</compile-change-summary>

</capabilities>
